# Authority and reconstruction method

This file governs the reconstruction dossier. It does not replace the repository's canonical authority contracts; it records how those contracts are applied while researching the invention.

## Authority order

The current Refactor authority stack establishes the following order of authority:

1. inventor-direct evidence;
2. direct-evidence index;
3. stable current product law;
4. historical inventor product law where unsuperseded;
5. working projections;
6. executable contracts;
7. observed development state;
8. historical counterexamples.

Historical implementation ABI, schema, deployment accidents, unfinished UI behavior and current branch shape do not become invention law simply because they are concrete.

## Required reading/load order before derived claims

A derived architectural claim must be reconciled against, in order:

1. inventor-direct requirement/correction evidence;
2. `CONSTITUTION.md` / constitutional product law;
3. current Invention Model;
4. pinned original-Laplace invention lineage;
5. inventor-direct synthesis/corrections, including the 2026-09-02 cognition clarifications;
6. mathematical/cognition records;
7. `AGENTS.md`, Operational Model, ISA and architecture boundaries;
8. requirement, acceptance, finish-line, roadmap and audit material;
9. implementation observations only after the above are loaded.

If an implementation and higher-authority requirement disagree, the implementation is classified as a counterexample/defect until evidence proves the requirement was explicitly superseded.

## Evidence classes used in this dossier

### DIRECT CURRENT LAW

Examples include explicit inventor corrections such as:

- physicality trajectory uses the GeometryZM datatype family rather than a line-only ontology;
- the concrete physical structure comes from modality/form/tier/recipe;
- packed trajectory/address data and real structural coordinates are different;
- the whole observation enters cognition before focus/topic selection;
- structural geometry cannot establish semantics;
- Gödel procedural discovery is not ordinary OODA execution.

### CURRENT PRODUCT LAW

Current architecture/contracts that are consistent with direct law, including universal identity, typed AST/Merkle DAG, execution boundaries, evidence separation, O(tier) runtime admission, typed perfcache lifecycle, cognition/completion, model symmetry and product-materialization laws.

### HISTORICAL INVENTOR EVIDENCE — UNSUPERSEDED

Older product/design evidence that remains valid where no later direct/current law contradicts it. This category requires explicit supersession checking.

### HISTORICAL / SUPERSEDED

Examples may include historical Hartonomous architectures that used SQL Server + Neo4j + Milvus, external LLM/agent orchestration, or the April 2026 broad naming of the Gödel Engine as the multi-scale OODA wrapper. These explain evolution; they cannot overwrite later direct/current distinctions.

### IMPLEMENTATION EVIDENCE

Source code, schemas, generated artifacts, tests, runtime screenshots, installed UI, workflow runs and receipts. These prove behavior/state, not intent by themselves.

### COUNTEREXAMPLE

Implementation evidence that violates higher-authority product law. Examples include source-first user workflows, lab/admin browser shells being treated as product information architecture, rank-1-topic cognition shortcuts, generic standing quantities mislabeled in UI, or packed trajectory payload treated as live geometry.

### SYNTHESIS

A conclusion supported by multiple primary sources but not explicitly stated as inventor law. Synthesis must identify its supporting evidence and remain falsifiable by later primary evidence.

### UNRESOLVED

Used whenever chronology, causality, required shape, or supersession cannot yet be established. No gap-filling.

## Date rules

Every dated claim must state its date source. Required format in `01_CHRONOLOGY.md`:

| Date | Date basis | Artifact | What it proves | What it does not prove |

Examples:

- GitHub repository `created_at` proves repository existence by that timestamp, not authorship time of every file later committed.
- A source header `Authored: 01/31/2016` is stronger evidence for that file's stated authorship date than a repository update timestamp, but still does not prove every later line existed then.
- Drive `created_at` proves the Drive object existed by that time, not that every idea in a revised document originated then.
- An issue creation timestamp proves when that issue record existed, not the first invention of the mechanism it documents.

## Research completeness rules

A domain/lineage pass is not considered complete because one representative source was found. Before making a lineage claim, the pass must search at least:

- named repositories already implicated by evidence;
- adjacent repositories in the same date band when names/descriptions indicate relevant data, game, GIS, automation, schema, AI or product work;
- Google Drive material for the same period/domain;
- original Laplace and Hartonomous lineage where the concept later appears;
- direct corrections that may supersede earlier interpretations.

The reconstruction explicitly rejects these shortcuts:

- `CIEDigital demonstrates generics` ⇒ stop researching earlier generic/schema work;
- `current Refactor has a UI` ⇒ infer intended UX;
- `current code uses one geometry subtype` ⇒ infer physicality ontology;
- `historical Hartonomous called Gödel multi-scale OODA` ⇒ collapse modern Gödel and OODA;
- `one performance proof exists` ⇒ infer product acceptance;
- `one source name matches another` ⇒ infer referential identity;
- `one structural metric is predictive` ⇒ promote it to semantics/truth.

## Causality standard

The dossier distinguishes:

- **chronological predecessor** — earlier relevant work exists;
- **recurring engineering practice** — same design tendency appears repeatedly;
- **explicit lineage** — primary source directly states the later mechanism derives from or generalizes the earlier work;
- **assistant synthesis** — evidence suggests continuity but direct causal statement has not been found.

No recurring practice is labeled direct causal ancestry without explicit evidence.

## Counterexample discipline

Screenshots and current code are valuable when used correctly. They can prove:

- the current product exposes implementation-centric workspaces;
- a user workflow requires source/provider knowledge;
- a page mislabels a standing quantity;
- a chat path returns no result;
- a graph renders raw/unhelpful implementation state.

They cannot prove those behaviors are intended Laplace architecture when higher-authority product evidence contradicts them.
