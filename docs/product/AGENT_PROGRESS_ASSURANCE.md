# Agent progress and continuation assurance

Status: executable-governance explanation, 2026-09-02. This document describes how future agents are constrained to preserve Laplace's governing invention and produce measurable progress. It does not create product law; the governing authority is the inventor-direct evidence, stable product law, executable contracts, and accepted tests.

## 1. Persistence stack

A future work session is not supposed to begin from the current source tree or a convenient open issue. It begins from the ordered authority stack.

The load order makes the following precede mutable work state:

```text
direct requirement evidence
-> Constitution
-> Invention Model
-> inventor-direct 2026-09-02 synthesis
-> Laplace mathematical research program
-> AGENTS working projection
-> architecture / ISA / boundaries / engineering law
-> executable requirements and acceptance
-> finish-line program
-> branch-estate closure contract
-> observed branch ledger
-> roadmap
-> continuation checkpoint
```

This means a branch, issue, prior agent summary, current implementation pattern, or stale checkpoint cannot overrule the invention.

## 2. Work selection is executable

`contracts/finish-line-program.json` defines the work-state machine, milestone exit predicates, mandatory owners, active sprint, anti-substitution matrix, repeated-defect escalation, progress accounting, and terminal evidence chain.

An active work item requires:

```text
owner
phase / milestone
dependencies
exit condition
immediate next action
```

Agents do not get to treat familiarity as priority. The current dependency graph and P0 branch-estate reconciliation govern work selection until updated by real dependency/evidence changes.

## 3. Progress means reducing an executable predicate

Activity is not progress.

The following alone do not count as implementation progress:

```text
new issue
new PR
new branch
documentation/status report
screenshot
successful load
shape-compatible artifact
repeated investigation
```

Progress is a measurable reduction or closure of an explicit exit predicate, acceptance obligation, prerequisite, or branch-reconciliation obligation.

Every agent handoff/work-session boundary therefore records a progress receipt containing at least:

```text
authoritative base/head
owning issue/PR
product behavior advanced
requirement/contract touched
exact files/runtime state changed
tests/acceptance executed and result
deliberate-defect status where applicable
remaining failed/open predicates
exact blocker when blocked
immediate next action
```

A partial result stays partial. It cannot become `fixed`, `done`, `delivered`, or product completion because an agent stopped working.

## 4. Anti-hyperfocus is machine-checked

Issue #184 and the mathematical research-program documents preserve the cross-cutting state distinctions. The finish-line contract now explicitly rejects, among other substitutions:

- rank-1 topic or token-class weighting for whole-observation interpretation;
- one global source-trust scalar replacing seeded priors plus earned participant standing;
- flattening the typed substrate before target operator generation;
- successful GGUF load or added head/layer count as proof of generated semantics;
- habit or muscle-memory fast paths bypassing current semantic validity.

Repeated independent leaf failures escalate to the generic owner after the declared threshold instead of allowing indefinite patch-by-patch churn.

## 5. Repository convergence prevents work loss

Issue #183 and `contracts/branch-estate-closure.json` require every unique non-main branch to have an explicit disposition and route to authoritative `main`. Unaccounted unique branch work is a P0 failure and blocks terminal acceptance.

This prevents a valid implementation from disappearing because one agent used another worktree or because a PR was superseded without behavior-level reconciliation.

## 6. CI is the mechanical gate

The finish-line and branch-estate contracts have executable tests and deliberate mutations registered in ordinary CTest. `main` is branch-protected and requires the `requirements`, `native (linux-dev)`, and `native (linux-sanitize)` checks. Once the governance PR lands, the research-program/load-order/progress assertions added to the finish-line test are part of those required native checks.

This is stronger than telling an agent to read documentation: changes that remove the required owners, research-program load order, progress receipt fields, anti-substitution controls, or deliberate-defect expectations are intended to fail CI.

No finite test suite can prove that every future agent will make a good engineering decision. The assurance model is therefore layered:

```text
ordered authority
+ explicit owner/dependency/exit state
+ no-orphan branch ledger
+ executable acceptance
+ deliberate mutations
+ protected required checks
+ exact progress receipts
```

An agent can still make a mistake. It should not be able to silently redefine the product, call activity completion, lose branch-only work, or merge a known protected invariant violation without leaving a failing evidence boundary.

## 7. Continuation after interruption

The mutable continuation checkpoint is loaded last and must be reverified against the repository and live runtime before use. Stale observations become unknowns; they never become product law.

After a correction, review finding, status question, or failed check, the agent continues the same safe dependency chain until:

- an executable boundary advances;
- a real blocker is established and the next unblocking action is explicit; or
- the user stops or changes direction.

Explanation alone is not a reason to abandon the next available implementation action.
